# @wunderio/node-agents

Isolated AI agent environment for node/npm projects. No DDEV required.

## What it is

`@wunderio/node-agents` brings the same secure, containerised agentic workflow
that Wunder.io uses for PHP/Drupal projects to node/npm projects:

- Isolated devcontainer with GitHub Copilot CLI
- A `node-project` Copilot skill covering the npm/yarn/pnpm workflow
- Wunder Quality System MCP integration
- Read-only managed security config (`copilot-managed-config.json`)
- `--cap-drop=ALL` + `no-new-privileges:true` hardening
- `GH_TOKEN` / `WQS_MCP_API_KEY` injected via devcontainer `remoteEnv`

## When to use this vs. the DDEV add-on

Use `@wunderio/node-agents` when your project is **not** a PHP/Drupal project
and does **not** use DDEV. If you already use DDEV, use the
`wunderio/ddev-agents` add-on instead.

## Prerequisites

- Node.js 20+ and npm on the host
- Docker (or Docker-compatible runtime) on the host

## Installation

```bash
npm install --save-dev @wunderio/node-agents
```

Recommended `package.json` scripts:

```json
{
  "scripts": {
    "agents:build": "agents build",
    "agents:setup": "agents set-up",
    "copilot": "agents copilot"
  }
}
```

## Authentication

### GitHub token

Create a GitHub Personal Access Token with **Copilot Requests: Read-only**
permission, then export it on your host:

```bash
export DDEV_AGENTS_GH_TOKEN=your_token_here
```

The token is passed into the container via `remoteEnv` and is never written to
the image or container filesystem.

### WQS API key (optional)

Export the Wunder Quality System MCP API key on your host:

```bash
export WQS_MCP_API_KEY=your_key_here
```

## Commands

All commands run inside the isolated agents container.

### `agents build`

Build the devcontainer image. Node.js version is auto-detected from `.nvmrc`
or `package.json` `engines.node`, with an optional override:

```bash
agents build
agents build --node-version 20
```

The resulting image (`<project>-agents:latest`) is reused as a build cache by
`agents set-up` and `agents start`.

### `agents set-up`

Build (if needed), start the container, generate MCP configs, and symlink
`~/.copilot` to `/workspace/.copilot` for persistence.

```bash
agents set-up
```

If `.devcontainer/devcontainer.json` already exists and was not generated by
this tool, `set-up` stops rather than overwriting it. Pass `--force` to replace
it deliberately:

```bash
agents set-up --force
```

### `agents copilot [args]`

Run GitHub Copilot CLI.

```bash
agents copilot
agents copilot -p "explain this code"
agents copilot --version
```

### `agents start` / `agents stop`

Start or stop the agents container.

### `agents npm [args]` / `agents npx [args]`

Passthrough to npm/npx inside the container.

```bash
agents npm install
agents npm run build
agents npx eslint .
```

### `agents exec <command> [args...]`

Run an arbitrary command inside the container.

```bash
agents exec -- node -v
agents exec -- git status
```

## Agent tooling: a skill, not an MCP server

The Copilot agent runs in the **same container** as your project source, with
the whole node toolchain on its `PATH`. It therefore runs `npm run build`,
`npm test` and friends with its own shell — no MCP round-trip is involved.

`agents set-up` writes two files into `~/.copilot` inside the container (which
is symlinked to `<project>/.copilot`, so nothing lands in your git tree):

| File | Contents |
|---|---|
| `skills/node-project/SKILL.md` | The npm/yarn/pnpm playbook: lockfile-based package-manager detection, canonical install/ci/run/build/test/lint commands, how to treat a failing suite, long-running commands, and guardrails |
| `copilot-instructions.md` | Facts detected for *this* project: name, Node.js version, package manager (and the lockfile it came from), and the scripts declared in `package.json` |

Both are regenerated on every `agents set-up`, so re-run it after changing your
lockfile or scripts.

The only MCP server registered for node projects is the remote Wunder Quality
System server.

### Why no MCP server?

The DDEV flavour uses [`@wunderio/wdrmcp`](https://www.npmjs.com/package/@wunderio/wdrmcp),
whose `command` and `check` executors require an `ssh_target` and always execute
over SSH into the DDEV `web` container. There, MCP is architecturally necessary:
the agent cannot otherwise cross the container boundary.

This flavour deliberately runs a single container, so there is no boundary to
cross. A local MCP server would only wrap shell commands the agent can already
run, at the cost of a second published npm package and a Copilot MCP registry
entry. Shipping a skill instead keeps `@wunderio/node-agents` self-contained.

## Security

- Token-based auth via host environment variables
- Managed config mounted read-only at `/home/vscode/.copilot-managed-config.json`
- Container runs with `--cap-drop=ALL` and `--security-opt no-new-privileges:true`
  (`sudo` is intentionally unavailable inside the container)
- `SSH_AUTH_SOCK` is cleared in `remoteEnv`
- Secrets are passed via `remoteEnv` only, never `containerEnv`, so they do not
  appear in the container's stored configuration

## Troubleshooting

**Container fails to start:** ensure Docker is running and the devcontainer CLI
can reach it. The first run may take several minutes to build the image.

**Copilot authentication fails:** verify `DDEV_AGENTS_GH_TOKEN` is exported in
the shell where you run `agents`.

**The agent does not know about your scripts:** re-run `agents set-up` after
changing `package.json` or your lockfile, then start a fresh Copilot session.
You can inspect what was installed with:

```bash
agents exec -- bash -lc 'cat ~/.copilot/copilot-instructions.md; ls ~/.copilot/skills'
```

Inside a Copilot session, `/skills` lists the discovered skills.

**`sudo` does not work:** this is intentional — the container drops all
capabilities and sets `no-new-privileges`, as described under Security above.
Use `docker exec -u root` from the host if you genuinely need root.
